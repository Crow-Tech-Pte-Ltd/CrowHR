## Context

Findings from the 13 Nov 2026 mobile audit, re-checked against the code. The owner's rule for this work: keep every feature and what each screen shows, and never lose, duplicate or re-time a punch.

## Decisions

1. **iOS queue file states.** `FilePunchQueueStore.load()` tells three cases apart: no file (`[]`), a file that can't be read now (throws: the phone is locked), and a file that reads but isn't punches (set aside as `queue.unreadable-<time>.json`, as before, then `[]`). `PunchQueue` no longer reads in `init`. Every operation first tries to read; until a read succeeds it never writes, never prunes and never sends (`DrainStop.locked`), so nothing older can be overtaken. A tap made meanwhile stays in memory and is appended after the stored punches, then saved, as soon as the file can be read. Lowering the protection class was rejected: the spec wants the file unreadable while locked.
2. **Tap time.** iOS takes a `PunchTap` (wall clock, uptime, boot session) from the queue's own clocks before awaiting the location (`PunchQueue.punch`). Android takes a `PunchTap` in `onTap`; while the permission dialog is open it is kept in saved state, so its time survives the activity being recreated. Fixtures give `deviceTime` explicitly and are unaffected; the server records `serverTime - elapsedMs`, which now counts from the tap.
3. **Android tap lifetime.** `AppGraph.appScope` (main thread, supervisor job) runs the location wait, the save and the drain. State the screen no longer shows is harmless to write. `PunchSync.request` right after the save covers a process that ends mid-send; the queue's mutex and the idempotency key keep a concurrent WorkManager drain from sending twice.
4. **Android store cache.** `EncryptedFileStore` keeps each successfully decrypted value (and the key index) in memory under the same monitor as today. `put` writes first and only then updates memory; `remove` and `clear` drop entries; a failed decryption isn't remembered. The files stay AES-GCM encrypted with the Keystore key. Memory holds only what the app has read or written while it is stored, which it already held decrypted while using it; sign-out removes it. The Keystore key handle is looked up once and looked up again if the Keystore refuses it. Each write is `fsync`ed before the rename.
5. **Android tab memory.** `ScreenMemory` keeps the last value of the Clock, Leave, Pay and Tasks loaders per connection, in memory only, cleared by `AppGraph.clearSession`. The existing rule "a reload keeps the current content until the new one arrives" then applies from the first frame, as on iOS. Payslip details are not kept.
6. **Android early refresh.** `StoredTokens.accessExpiresAtEpochMs` (nullable, so tokens stored by earlier versions still read) is set from `expiresIn` at request time. `ApiClient` renews within 60 s of expiry through the same single-flight `NativeAuth.refresh`; if the server can't be reached it still tries the current token.
7. **iOS sessions.** `AuthSession` keeps a rotated pair in memory even if the Keychain refuses it and saves it again on the next request; a refresh that finishes after sign-out is dropped; `clear()` deletes only its own device session's tokens. `AppModel` reuses one `AuthSession` per connection when switching back (a new sign-in starts a new one) and ignores a sign-out callback from a session that is no longer current.

## Risks / Trade-offs

- iOS now answers a redirected punch with "retry later" (its existing rule for anything that isn't a 4xx), while Android's rule from `punch-queue-cases.json` refuses it. Aligning them is the pending owner decision on that fixture rule.
- Stale tab content shows for one round trip on Android (as on iOS) instead of a spinner. The Clock button shows the last known state instead of defaulting to "Clock in" while loading.
