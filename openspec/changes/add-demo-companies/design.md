## Context
- The in-browser demo runs core against PGlite in the visitor's browser (`deps.demoMode`), one organisation, persona sign-in (`packages/core/src/auth/demo.ts`). The mobile apps can't use it: they talk to a real server over HTTPS.
- The apps (1.0.0, in the stores) already: open `crowhr://connect?server=<url>&org=<slug>` links (Android intent filter, iOS URL scheme) and QR codes; read `GET /api/v1/meta?org=` and show "Demo server with fictional data" when `demo` is true; sign in by opening `/api/v1/native/authorize` in the system browser, which redirects to `/sign-in/<slug>?native=<id>`; any sign-in method on that page that calls `completeNativeSignIn` returns to the app. So the server side alone can make a phone demo work for the apps already published. They refuse an organisation whose meta lists no sign-in method (`no_sign_in_methods`), and show only each method's `displayName`.
- `scripts/seed-sample-company.ts` installs Kopi Kaki on a running server (store reviewers): seeds in a scratch PGlite (`packages/demo/src/sample-company`), then `copyOrganisation` into the server's database. It refuses when the slug or an email exists: `users.email` is unique across organisations (so is `organisations.uen`).
- `audit_events` is append-only by trigger (`drizzle/0002_audit_immutability.sql`) with a per-organisation hash chain.
- Core has no timers; the server drives `tick` (`apps/server/src/scheduler.ts`).

## Goals / Non-Goals
Goals: anyone can try Crow HR end to end (phone app and web, the same company) without credentials or typing; each visitor's data is their own; nothing about it can be enabled on, or leak into, a real install; nothing entered is retained after the copy ends (Daniel, 13 Nov 2026).
Non-goals: changing the apps (that waits for the next version); demo companies on the static in-browser demo; keeping a demo company longer than its expiry; real email from demo companies.

## Decisions
1. **Server mode, off by default.** `DEMO_COMPANIES=1` (server config → `deps.demoCompanies = { ttlHours, poolSize, maxLive, hourlyLimitPerNetwork, dailyLimitPerNetwork, uploadQuotaBytes, provision, personaInfo }`). Without it every new route answers 404, sessions of existing demo companies stop working, and no organisation can become a demo company. It is not `deps.demoMode`: the server stays a normal server for its other organisations (hr-demo also hosts the Kopi Kaki review organisation and the demo's Singpass relying party). A `DEMO_COMPANY_*` setting without `DEMO_COMPANIES=1` stops startup with a message, as does an hourly limit above the daily one.
2. **The flag lives on the organisation and is set only at insert.** `organisations.demo_expires_at timestamptz NULL` and `demo_claimed_at` (migration 0018, partial index on the expiry). A trigger refuses any UPDATE that changes it from NULL to a value or from a value to NULL, so a real organisation can never be turned into a demo company (and so become deletable). Moving a demo company's expiry (value to value) is allowed: claiming a pool copy uses it, and so does the purge CLI.
3. **One private copy per visitor, from a pool.** Seeding takes seconds of CPU, so the scheduler keeps `poolSize` (default 3) unclaimed copies ready and refills one per tick (skipping the tick while another seed runs). A pool copy is inserted with `demo_claimed_at NULL` and `demo_expires_at = seeded + 24 h`: nobody can sign in to it before it is handed out, and one nobody claims within a day is swept and replaced (its history is dated to its seeding day). `POST /api/v1/demo-companies` claims the oldest pool copy (`FOR UPDATE SKIP LOCKED`; sets `claimed_at`, starts the expiry clock from the claim: `demo_expires_at = now + ttl`), or seeds one inline if the pool is empty (one seed at a time per process, at most 3 visitors waiting, the 4th gets 503 "try again in a minute"). Each copy: slug `demo-` + 12 lowercase base32 characters (60 bits; the slug is the key to that copy, see 6), the sample company and its people, emails at `<local>@<slug>.kopikaki.example` (unique, reserved TLD; seeded with that domain so audit labels match, work emails rewritten), no passwords (cleared before the copy, so accounts can't sign in with a password), `organisations.uen` NULL (it is unique on the server; the profile keeps its UEN), history June–October 2026 plus the catch-up to the seeding day. `prepareSampleCompany` takes `org: { slug, emailDomain, name? }` and `passwords: "random" | "none"`; the store-review script keeps its values. Each copy is seeded in its own in-memory PGlite (the scratch app uses the demo PBKDF2 hasher, never the server's), then `copyOrganisation(…, { organisation: { slug, uen: null, demoExpiresAt, demoClaimedAt } })` inserts the flag on insert. The provisioner lives in `packages/demo` (`createDemoCompanyProvisioner`) and is injected by apps/server, which loads it (and PGlite) on the first seed only.
4. **Caps.** Creation per network (client IP after `TRUSTED_PROXIES`, /64 for IPv6, IPv4-mapped as IPv4) per clock hour (default 5) and per UTC day (default 20), and `maxLive` (default 300) handed-out copies in total (the pool never grows past `maxLive` minus those). Past a cap: 429 `rate_limited` with `details.retryAt` and `Retry-After` (the window's end, or the earliest live expiry for `maxLive`); the try page says when to come back. Fixed windows in `auth_throttle` like the demo Singpass starts, but keyed by an HMAC of the network under the server's key (`SECRET_PURPOSES.demoNetwork`), so no IP address is stored, and each counter is deleted when its window ends (an hour, a day; every tick, mode on or off).
5. **Persona sign-in for demo companies.** `GET /api/v1/auth/demo/personas?org=<slug>` and `POST /api/v1/auth/demo/sign-in { membershipId, org?, native? }` keep their browser-demo behaviour (no `org` needed, 204) and also serve a demo company when `deps.demoCompanies` is on, `org` names it, and it is handed out and not expired. Anything else stays 404: a real organisation's member, a membership of another demo company, a pool copy, an expired copy, a missing `org`, a user who also belongs to another organisation. With `native` (a pending native request for that organisation) the route calls `completeNativeSignIn` and answers 200 `{ redirectTo }`; otherwise 204 with a browser session. The session's method is `password` with MFA satisfied, as in the browser demo. Audit: `auth.signed_in` with `method: "demo_persona"` (`client: "native"` for the app). The persona list carries `persona: { key, label, blurb, order }` from `deps.demoCompanies.personaInfo` (the server's labels, so the web app needs no demo build). Featured: owner, HR admin, payroll admin, manager (Siti) and employee **Hafiz**, not the browser demo's Jun Jie, whose manager changes on 1 Dec 2026 by a scheduled transfer; Hafiz's requests always reach Siti. The sign-in page shows the persona picker for a demo company, in the browser and in the app's sign-in browser (from `GET /api/v1/auth/methods?org=` → `demoCompany: { expiresAt }`, `password.enabled: false`, no providers), and no password form.
6. **Not listed, not guessable.** `GET /api/v1/meta` without `org` never lists demo companies, and `orgSlugRequired` is true on a server with demo companies (it never falls back to "the only organisation"; neither does `/auth/methods`). With `org=<demo slug>` it answers `demo: true` and lists one sign-in method, `{ kind: "password", displayName: "Pick a person (demo company, no password)" }`: the 1.0.0 apps need one, and `kind` is a closed enum in the v1.0 contract. Slugs are random (decision 3), so knowing the server tells you nothing about other visitors' copies. Demo companies don't count as "the only organisation" (`onlyOrganisation`) or as setup done (`isSetupRequired`).
7. **Guard rails, server-side.** For a session in a demo company (`AuthContext.demoCompany`, loaded with the membership) the server answers 403 `disabled_in_demo` "Not available in a demo company…" on the routes marked `refusedInDemoCompany` (route guard; the OpenAPI document lists the code): `PATCH /security/settings`, `POST/PATCH/DELETE /security/providers`, `POST /members/invitations`, `POST /members/{id}/invitation/resend`, `POST /members/{id}/password-reset-link`, `POST /members/{id}/mfa/reset`, `POST /members/{id}/sign-out-everywhere`, `DELETE /members/{id}/sessions/{sessionId}`, `POST /me/password`, the four MFA routes under `/me/mfa`, and `POST /auth/switch-organisation`. Public routes check the organisation: password reset request and completion, invitation acceptance. `inviteMember` refuses a demo company itself (an invitation would reuse an existing account by email and tie a real person's account to a visitor's copy); a hire there records the employee and skips the invitation. There is no user-email change or mailer-settings route to refuse. No email is sent: a demo company's requests run without the mailer, and the outbox suppresses anything queued for one. Re-authentication is not asked for in a demo company (sign-in is one tap; its people have no password). Uploads (`files`: receipts, documents, letters) count against `uploadQuotaBytes` (default 25 MB), refused with 413 `file_too_large` naming the limit; the company logo (one file, at most 1 MB) is not counted. Everything else (leave, claims with receipts, attendance, rosters, payroll runs, documents, reports, exports, approvals) works as in a real company. Device sessions in a demo company store the platform name ("Android phone", "iPhone") instead of the device's own name, also in the "new device" notice and audit event.
8. **Expiry sweep.** Each tick deletes up to 5 expired demo companies (on every server, mode on or off, so nothing outlives its expiry): every organisation-scoped row (the table order `copyOrganisation` derives, now `tablesInDependencyOrder()` in core, in reverse), memberships, sessions and device sessions, audit events, users who belong to no other organisation and their recovery codes, the organisation row, and then the files (keys from `files`, the logo and employee photos, plus `FileStore.deletePrefix("org/<orgId>/")`). In the same transaction it sets `set_config('crowhr.purge_demo_org', '<orgId>', true)`; the audit trigger allows DELETE only when that setting equals the row's `org_id` **and** that organisation has a non-null `demo_expires_at` before the database clock's `now()`. UPDATE and TRUNCATE stay refused for everyone. The purge also re-reads the organisation under a lock and does nothing for one without a past demo expiry. Tests prove a real organisation's audit events can't be deleted even with the setting, that the sweep never touches organisations without the flag, and that sessions, device sessions, users and files go. Sessions of an expired copy stop working at once, before the sweep. `crowhr demo-companies purge [--expired]` ends and deletes every demo company (or only the expired ones).
9. **Try page.** `/try` in the web app (public; "Page not found" unless `GET /api/v1/demo-companies/config` answers): 1) get the app (Google Play link; App Store "coming soon" until `APP_STORE_URL` is set, `apps/web/src/me/app-stores.ts`, shared with My profile → Mobile app); 2) "Start my demo company"; 3) open it: on a phone (user agent), "Open in the Crow HR app" (`crowhr://connect` on iPhone; on Android an `intent://connect…#Intent;scheme=crowhr;package=crowtech.crowhr;S.browser_fallback_url=<Play listing>;end` link) plus "Open in this browser"; on a computer, a QR code of the `crowhr://connect` link plus "Open in this browser". It also shows the server address and company code to type instead (the Android app's manual entry has no organisation field, so it says to use the link or QR code there), when the copy expires, and things to try. The visitor's current company is kept in `localStorage` (`crowhr.tryCompany`) so coming back shows it again until it expires. A demo company's pages show a slim "Demo company" banner with the end date; an ended (or unknown demo-looking) slug's sign-in page says "This demo company has ended" with a link to start a new one (`/auth/methods` 404 with `details.demoCompanyEnded`; the native authorize page says the same).
10. **Links.** In-browser demo (About this demo, and the demo banner shown on every screen including sign-in: "Try it on your phone"), docs (mobile apps page: "Try it with a demo company"), crow.sg product page (mobile section) link to the try page. The URL comes from one setting per site (`VITE_TRY_URL` for the demo build, `TRY_URL`/`TRY_LIVE` in `apps/docs/src/lib/links.ts`, the landing config). Until launch the demo shows no link and the docs say the try page opens soon.
11. **Privacy: nothing is retained** (Daniel, 13 Nov 2026). Every visitor gets their own copy; what they type or photograph, the platform name and the sign-in records stay in it until it expires and are then deleted with it (decision 8). The start limits keep counts only, never an IP address, for at most a day (decision 4). The try page says so in one sentence and links the apps' privacy policy; no "Demo server" section is added to it (task 4.3: not needed, nothing is retained). Whether the demo server affects the stores' "Data Not Collected" answers belongs to the open legal review (add-mobile-apps 4.3): it is optional, user-chosen and not the app's purpose.

## Measurements (task 4.2)
Measured on naan, 13 Nov 2026 (Intel Core Ultra 7 356H, 16 threads: the same CPU as S4), Node 25, with `createDemoCompanyProvisioner` and the server's own PGlite scratch database, one copy after another:
- **Time:** 17.6–18.3 s wall and 21–23 s CPU per copy (4 copies into PostgreSQL 15, 3 into PGlite; no trend). In vitest, two copies took 42 s together.
- **Memory (PostgreSQL target, as on a server):** 323 MB resident before the first seed; peak 985 MB during the first and about 1.12 GB during the next ones; about 950 MB after each, stable over four copies (no growth).
- **Size:** about 5 MB of database (PGlite: 21 MB after two copies, including the empty schema) and about 180 KB of files per fresh copy.
- **Defaults kept:** TTL 72 h, pool 3, `maxLive` 300, 5 starts per network per hour, 20 per day, 25 MB uploads. A pool of 3 refills in about 3 minutes (one per tick). At the cap, 300 copies are about 1.5 GB of database plus at most 7.5 GB of uploads in the worst case; seeding them all costs under 2 CPU-hours spread over 3 days. Give the app container at least 1.5 GB of memory with the mode on.

## Risks / Trade-offs
- [Abuse: offensive text or images in a visitor's own copy] → copies are private (nobody else sees them unless given the code), quota-limited and deleted after the TTL.
- [Load: seeding uses CPU and memory] → one seed at a time per process, at most 3 waiting, pool refill only when below `poolSize`, caps per network and in total; measured above. The catch-up to the seeding day grows with time, so seeding slows over the months (limitations).
- [The audit exception weakens immutability] → restricted by database trigger to demo-flagged organisations whose flag can only be set at insert, past expiry (database clock), inside the sweep's transaction; tested.
- [Copy slug leaks, e.g. a shared screenshot] → that copy only; it expires.
- [A visitor ties a real account to a copy] → invitations are refused in demo companies at the service level, persona sign-in refuses a user with another membership, and switching organisation is refused there.
- [A visitor squats a real company's UEN] → a demo company's UEN is never written to `organisations.uen`.
- [Backups hold demo companies] → a backup on the demo server contains the copies live at that moment; keep scheduled backups off there (hr-demo has `BACKUP_TIME=off`).
- [hr-demo must not change during the App Store review] → ship the code now, turn the mode on after Apple's decision.

## Migration Plan
Migration 0018 adds `organisations.demo_expires_at`, `organisations.demo_claimed_at`, a partial index, the flag trigger and the amended audit trigger. No data changes for existing organisations (NULL). The image keeps PGlite (27 MB) and the sample-company seed (`packages/demo/src`). Rollback: turning `DEMO_COMPANIES` off stops creation and sign-in and ends the copies' sessions; the scheduler still deletes each copy at its expiry, and `crowhr demo-companies purge` deletes them all at once.
