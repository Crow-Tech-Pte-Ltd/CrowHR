## Context
- The in-browser demo runs core against PGlite in the visitor's browser (`deps.demoMode`), one organisation, persona sign-in (`packages/core/src/auth/demo.ts`). The mobile apps can't use it: they talk to a real server over HTTPS.
- The apps (1.0.0, in the stores) already: open `crowhr://connect?server=<url>&org=<slug>` links (Android intent filter, iOS URL scheme) and QR codes; read `GET /api/v1/meta?org=` and show "Demo server with fictional data" when `demo` is true; sign in by opening `/api/v1/native/authorize` in the system browser, which redirects to `/sign-in/<slug>?native=<id>`; any sign-in method on that page that calls `completeNativeSignIn` returns to the app. So the server side alone can make a phone demo work for the apps already published.
- `scripts/seed-sample-company.ts` installs Kopi Kaki on a running server (store reviewers): seeds in a scratch PGlite (`packages/demo/src/sample-company`), then `copyOrganisation` into the server's database. It refuses when the slug or an email exists: `users.email` is unique across organisations.
- `audit_events` is append-only by trigger (`drizzle/0002_audit_immutability.sql`) with a per-organisation hash chain.
- Core has no timers; the server drives `tick` (`apps/server/src/scheduler.ts`).

## Goals / Non-Goals
Goals: anyone can try Crow HR end to end (phone app and web, the same company) without credentials or typing; each visitor's data is their own; nothing about it can be enabled on, or leak into, a real install.
Non-goals: changing the apps (that waits for the next version); demo companies on the static in-browser demo; keeping a demo company longer than its expiry; real email from demo companies.

## Decisions
1. **Server mode, off by default.** `DEMO_COMPANIES=1` (server config → `deps.demoCompanies = { ttlHours, poolSize, maxLive, hourlyLimitPerNetwork, dailyLimitPerNetwork, uploadQuotaBytes }`). Without it every new route answers 404 and no organisation can become a demo company. It is not `deps.demoMode`: the server stays a normal server for its other organisations (hr-demo also hosts the Kopi Kaki review organisation and the demo's Singpass relying party).
2. **The flag lives on the organisation and is set only at insert.** `organisations.demo_expires_at timestamptz NULL` (migration). A trigger refuses any UPDATE that changes it from NULL to a value or from a value to NULL, so a real organisation can never be turned into a demo company (and so become deletable). Extending a live demo company's expiry is allowed (not needed in v1).
3. **One private copy per visitor, from a pool.** Seeding takes seconds of CPU, so the scheduler keeps `poolSize` (default 3) unclaimed copies ready and refills one per tick. `POST /api/v1/demo-companies` claims one (sets `claimed_at`, starts the expiry clock from the claim: `demo_expires_at = now + ttl`), or seeds one inline if the pool is empty. Each copy: slug `demo-` + 12 lowercase base32 characters (60 bits; the slug is the key to that copy, see 6), the sample company's name and people, emails at `<slug>.kopikaki.example` (unique, reserved TLD), no passwords (accounts can't sign in with a password), history dated relative to the seeding day. `prepareSampleCompany` takes `{ slug, emailDomain, orgName? }` instead of the fixed `SAMPLE_ORG`; the store-review script keeps its current values.
4. **Caps.** Creation per network (client IP after `TRUSTED_PROXIES`, /64 for IPv6) per hour (default 5) and per day (default 20), and `maxLive` (default 300) live copies in total; past a cap the try page says when to come back. The same limiter shape as the demo Singpass starts.
5. **Persona sign-in for demo companies.** `GET /api/v1/demo/personas?org=<slug>` and `POST /api/v1/demo/sign-in { membershipId, org?, native? }` keep their browser-demo behaviour and also serve a demo company when `deps.demoCompanies` is on and the membership's organisation has `demo_expires_at > now`. Anything else stays 404. With a pending native request for that organisation, the route calls `completeNativeSignIn` and returns the app redirect URL instead of starting a browser session. Audit: `auth.signed_in` with `method: "demo_persona"`. The sign-in page shows the persona picker for a demo company (from `GET /api/v1/auth/methods?org=` → `demoCompany: { expiresAt }`), and no password form.
6. **Not listed, not guessable.** `GET /api/v1/meta` without `org` never lists demo companies, and `orgSlugRequired` is true on a server with demo companies. With `org=<demo slug>` it answers `demo: true`, so the apps show their demo notice. Slugs are random (decision 3), so knowing the server tells you nothing about other visitors' copies.
7. **Guard rails, server-side.** For a session in a demo company the server refuses, with "Not available in a demo company", these routes: security and sign-in settings, SSO providers, member invitations and email changes, password set/change/reset, MFA enrolment, API/device token admin beyond the visitor's own device sessions, mailer settings. Outgoing email is never sent (no mailer for demo companies). Uploads count against `uploadQuotaBytes` per company (default 25 MB). Everything else (leave, claims with receipts, attendance, rosters, payroll runs, documents, reports, exports, approvals) works as in a real company. Device sessions in a demo company store the platform name ("Android phone", "iPhone") instead of the device's own name.
8. **Expiry sweep.** Each tick deletes up to N expired demo companies: every organisation-scoped row (the table list and order `copyOrganisation` already derives, in reverse), memberships, users who belong to no other organisation, device sessions, and the files under `org/<orgId>/`. In the same transaction it sets `SET LOCAL crowhr.purge_demo_org = '<orgId>'`; the audit trigger (migration) allows DELETE only when that setting equals the row's `org_id` **and** that organisation has a non-null `demo_expires_at` in the past. UPDATE stays refused for everyone. A test proves a real organisation's audit events can't be deleted even with the setting, and that the sweep never touches organisations without the flag.
9. **Try page.** `/try` in the web app (public; 404 page unless `GET /api/v1/demo-companies/config` says the feature is on): 1) get the app (Google Play link; App Store "coming soon" until its URL is set, same constants as My profile → Mobile app); 2) "Start my demo company"; 3) open it: on a phone, "Open in the Crow HR app" (`crowhr://connect`, and on Android an `intent://` link whose fallback is the Play listing) plus "Open in this browser"; on a computer, a QR code of the `crowhr://connect` link (the app's scanner or the phone camera) plus "Open in this browser". It also shows the server address and company code to type instead, and when the copy expires. The visitor's current company is kept in `localStorage` so coming back shows it again until it expires.
10. **Links.** In-browser demo (About this demo, and the sign-in page's demo banner), docs (mobile apps page: "Try it with a demo company"), crow.sg product page (mobile section) link to the try page. The URL comes from one setting per site (`VITE_TRY_URL` for the demo build, a docs constant, the landing config).
11. **Privacy.** The demo server is operated by Crow Tech, so a demo company is data Crow Tech holds for up to its expiry: whatever the visitor types or photographs, the platform name, and IP addresses for the caps (counts only, kept a day). The try page says so in one sentence and links the privacy policy, which gets a "Demo server" section before launch. Whether this affects the stores' "Data Not Collected" answers belongs to the open legal review (add-mobile-apps 4.3): the demo server is optional, user-chosen and not the app's purpose.

## Risks / Trade-offs
- [Abuse: offensive text or images in a visitor's own copy] → copies are private (nobody else sees them unless given the code), quota-limited and deleted after the TTL.
- [Load: seeding uses CPU and memory] → one seed at a time, pool refill only when below `poolSize`, caps per network and in total; measured before launch on S4.
- [The audit exception weakens immutability] → restricted by database trigger to demo-flagged organisations whose flag can only be set at insert, past expiry, inside the sweep's transaction; tested.
- [Copy slug leaks, e.g. a shared screenshot] → that copy only; it expires.
- [hr-demo must not change during the App Store review] → ship the code now, turn the mode on after Apple's decision.

## Migration Plan
Migration adds `organisations.demo_expires_at`, `organisations.demo_claimed_at`, the flag trigger and the amended audit trigger. No data changes for existing organisations (NULL). Rollback: turning `DEMO_COMPANIES` off stops creation and sign-in; existing copies are purged by the next start with the mode on, or by `crowhr demo-companies purge` (CLI).
